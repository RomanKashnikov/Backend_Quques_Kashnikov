# Как устроен backend и что объяснять на защите

## Путь запроса

Клиент (Swagger/Postman) → HTTP-запрос → проверка JWT → проверка роли → контроллер → методы модели → EF Core → SQLite → HTTP-ответ с JSON.

`Program.cs` собирает приложение: регистрирует сервисы, базу, JWT и Swagger, создаёт начальные данные и задаёт порядок middleware. ASP.NET Core сам создаёт контроллер и передаёт ему AppDbContext через внедрение зависимостей. Запись `public class UsersController(AppDbContext db)` — первичный конструктор C# 12: `db` доступен методам класса.

Атрибут `[ApiController]` включает стандартную обработку ошибок входных данных. `[Route("api/users")]` задаёт адрес ресурса. `[HttpGet]`, `[HttpPost]` и другие атрибуты связывают методы класса с HTTP-операциями.

## Три основные модели

### AppUser

Хранит ID, номер пропуска, имя, фамилию, группу, роль и хеш пароля.

- `Update` проверяет роль и обязательные строки, нормализует пробелы и меняет профиль.
- `SetPassword` проверяет длину и вычисляет хеш с помощью стандартного PasswordHasher.
- `CheckPassword` проверяет пароль без хранения его исходного текста.
- `SecurityStamp` меняется при изменении профиля или пароля. JWT содержит его копию; несовпадение при следующем запросе аннулирует старый токен.

У свойств доменных данных закрытые сеттеры: внешняя логика должна вызывать методы модели, а не произвольно присваивать значения. EF Core умеет работать с такими свойствами. Хеш и SecurityStamp помечены JsonIgnore и не выдаются клиенту.

### StudyQueue

Хранит предмет, название работы, преподавателя, группу, аудиторию, примечание, даты, необязательный лимит и состояние жизненного цикла.

- `Update` проверяет даты, лимит и возможность редактирования.
- `GetStatus` вычисляет Scheduled/Open/Closed на текущий момент либо возвращает Completed/Cancelled.
- `EnsureCanJoin` проверяет, что запись открыта и есть свободное место.
- `Finish` завершает или отменяет очередь.

В базе хранится Lifecycle = Active/Completed/Cancelled. Scheduled/Open/Closed вычисляются по серверному времени при запросе, поэтому не нужен таймер, меняющий строку БД каждую секунду. Начало мероприятия само по себе не закрывает запись, если closesAt не задано.

### QueueEntry

Связывает пользователя и очередь. Содержит внешние ключи, время добавления, Sequence и примечание.

- Конструктор проверяет корректность идентификаторов и последовательности.
- `UpdateNote` проверяет длину примечания.

Sequence задаёт относительный порядок внутри очереди. Это не отображаемое место: после удаления середины списка Sequence может иметь пропуски. Отчёт сортирует оставшиеся записи и присваивает позиции 1, 2, 3… . Изменять позицию через PUT нельзя.

DTO из `Contracts/Requests.cs` — вспомогательные формы HTTP-запросов, а не дополнительные предметные модели. Например, NoteRequest содержит только примечание: клиент не может подменить пользователя или Sequence при обновлении записи.

## База и связи

`Data/AppDbContext.cs` описывает три таблицы: Users, Queues, Entries.

- Users 1 → N Entries.
- Queues 1 → N Entries.
- Уникален номер пропуска.
- Уникальна пара (очередь, пользователь), что запрещает повторное участие.
- Уникальна пара (очередь, Sequence), что запрещает одинаковый порядковый номер.
- При удалении очереди записи удаляются каскадно.
- Удаление пользователя с записями запрещено, чтобы не оставлять записи без участника.

EF Core преобразует LINQ к DbSet в SQL. `AsNoTracking` используется при чтении, когда не требуется сохранять изменения загруженных сущностей. `SaveChangesAsync` сохраняет изменения одной операции в транзакции. Начальные учётные записи и демонстрационная очередь добавляются в `SeedData.Initialize`.

Для конкурентных операций в Program.cs используется SemaphoreSlim: в одном процессе запросы изменения выполняются по очереди, включая проверку количества участников и сохранение. Поэтому два запроса на последнее место не могут одновременно пройти проверку. Уникальные индексы дополнительно обеспечивают целостность данных. Это учебное решение на один экземпляр приложения, а не распределённая блокировка.

## CRUD и бизнес-правила

CRUD: Create — POST, Read — GET, Update — PUT, Delete — DELETE. PATCH в этой работе отдельно используется для смены состояния очереди.

Контроллеры отвечают за HTTP, поиск объектов и проверки между моделями. Например, EntriesController проверяет совпадение группы участника и очереди, отсутствие повторной записи, затем вызывает `queue.EnsureCanJoin` и создаёт QueueEntry. Сами классы модели содержат правила, относящиеся к их собственным данным.

Примеры правил: последние права администратора нельзя убрать; номер пропуска нельзя дублировать; нельзя записываться до открытия; нельзя превышать лимит; нельзя менять группу объекта с существующими записями.

## Четыре сводных запроса и LINQ

1. **Участники очереди:** карточка очереди + Join записей с пользователями. Возвращает предмет, работу, имена и позиции.
2. **Заполненность:** GroupJoin очередей и записей. Для каждой очереди считаются участники и свободные места. Включены и пустые очереди, а для неограниченной вместимости availablePlaces = null.
3. **Расписание пользователя:** профиль + Join его записей с очередями. Возвращает мероприятия, аудитории и даты. Включает также завершённые мероприятия; это список всех записей пользователя, а не только будущих.
4. **По предметам:** для каждой очереди вычисляется число записей, затем GroupBy и Sum дают число очередей и суммарное число записей по предмету. Один человек в двух очередях считается как две записи.

Пример обязательного Where:

```csharp
db.Users.Where(u => group == null || u.GroupName == group)
```

Where оставляет пользователей выбранной группы. Если фильтр не передан, возвращает всех.

Пример Select из отчёта:

```csharp
rows.Select((row, index) => new { position = index + 1, participant = row })
```

Select преобразует каждую строку в форму ответа и добавляет место. `ToListAsync` выполняет запрос к БД; последующая нумерация выполняется в памяти. Join в синтаксисе `from ... join ... select ...` — тоже LINQ.

## Аутентификация и авторизация

Аутентификация отвечает «кто это?», авторизация — «что ему можно?».

1. Клиент отправляет номер пропуска и пароль в login.
2. Сервер проверяет хеш и возвращает подписанный JWT на один час.
3. Клиент передаёт заголовок `Authorization: Bearer <токен>`.
4. JwtBearer проверяет подпись, издателя, аудиторию и срок действия.
5. Дополнительная проверка сверяет пользователя и SecurityStamp с БД.
6. `[Authorize]` допускает любого вошедшего пользователя; `[Authorize(Roles = "Admin")]` допускает только администратора.

JWT подписан, но не зашифрован: секреты в него не помещаются. Ключ генерируется случайно при первом запуске и хранится отдельно от исходного кода. App_Data исключён из Git и пакета публикации. Swagger доступен и в Release специально для сдачи.

## Что можно сказать на защите

«Разработан Web API для управления очередями на учебные мероприятия. Модель состоит из пользователя, очереди и записи пользователя в очередь. Классы не только хранят данные, но и проверяют правила. Для всех моделей реализован CRUD. Четыре сводных запроса используют связанные данные и LINQ. Вход выполняется по номеру пропуска и паролю с выдачей JWT.
